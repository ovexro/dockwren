# Features

Everything Dockwren does today, in detail. The short version is in the [README](../README.md).


- Single-admin login: strong generated password, Argon2id hash, `HttpOnly` + `SameSite=Strict`
  session cookie, login rate limit, sessions that survive restarts.
- Browser hardening on every response: Content-Security-Policy (own origin only, no framing, no plugins),
  `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: same-origin`, a restrictive Permissions-Policy, and
  HSTS when the panel is reached over HTTPS through a proxy or tunnel.
- Overview: all containers (running or not) with image, state and status, refreshed every 5 s. Below the tiles it shows the hostname, OS, uptime, Dockwren version and (once apps are installed) the time since the last backup.
- Status API for monitoring: `sudo -u dockwren env DOCKWREN_DATA=/var/lib/dockwren dockwren status-token` prints a read-only token once (only its hash is kept; running it again replaces it, `--revoke` deletes it). `curl -H "Authorization: Bearer <token>" https://<panel>/api/status` then returns JSON with each app's health, last backup time and snapshot count, image scan counts, and the newest backup overall. No hostnames, ports or secrets; the token cannot sign in or change anything. For Prometheus, scrape `/api/metrics` with the same token (`authorization: {type: Bearer, credentials: <token>}`): `dockwren_app_healthy`, `_public_up`, `_update_available`, `_backup_snapshots`, `_last_backup_timestamp_seconds` and the image-scan counts per app, plus `dockwren_last_backup_timestamp_seconds`.
- Resource graphs: CPU, memory, network and disk space as plain one-colour lines (last 1 h, 24 h, 7 days or 30 days), plus CPU/memory per running container. Sampled every 10 s; the 1 h and 24 h views live in memory, while 5-minute averages are kept 30 days in `metrics.log` in the data directory and survive restarts. A disk above 85% is flagged.
- Start, stop (with confirmation) and restart a container; log viewer (last 200 lines, refreshed every 5 s). Search box, level filter (warnings and errors, errors only) and time range (15 minutes to 24 hours) look through up to the last 20,000 lines, show the newest 500 matches and keep refreshing; **Download** saves all matches as a text file.
- App catalog with icons and install forms (generated passwords, per-field hints).
- Add your own stack: paste a Compose file and Dockwren runs it as a managed app, after checking it against a strict allow-list (see [STACKS.md](STACKS.md)). Later, **Edit stack** on the Apps page (also for adopted stacks) changes the file or its environment: the new file gets the same checks, a backup is taken first, and if the stack does not come back healthy the old file is put back. Earlier versions are kept (last 20) and can be loaded back with a diff.
- Adopt a running Compose project: Apps → Add an app → **Scan for other Compose projects** lists Compose projects on the server that Dockwren did not create. One that passes the same checks as a pasted stack and keeps its data in named volumes or plain host folders (not system folders such as `/etc`) can be adopted under a name you choose. Dockwren copies its compose file and `.env` into its own folder and only accepts it when `docker compose config --hash` matches the running containers exactly, so nothing is stopped, restarted or recreated. The original files stay untouched. Afterwards you get logs, start/stop, alerts and a public address like for any app. Backups of an adopted app also cover its named volumes and its host folders (archived where they are, nothing is moved): the stack is stopped for a few seconds while they are archived (so databases stay consistent), then started again; restore, verify and off-host copies work the same as for other apps. A restore puts a host folder back after moving the current one to `<folder>.pre-restore-<time>` (nothing is deleted). Restore tests and duplicating are skipped for stacks with host folders, because a second copy would share them. Removing an adopted app deletes its volumes, never its host folders. The panel must be able to read the compose file (it cannot see `/home`).
- Upstream version heads-up: once a day the panel asks Docker Hub or GitHub's registry (anonymous, only the image name is sent) whether each installed app's main image has a newer tag with the same shape (same `-apache`/`-alpine` suffix and number of parts). The Apps page shows "Upstream has 28.4.0" (a new major is listed separately) and one notification is raised. It never changes anything: apps move to new versions through the tested template updates that ship with Dockwren releases. Turn it off in Settings → Notifications.
- Updates with automatic rollback when the new version is not healthy, and optional migration
  steps per template.
- Backups (files plus database dumps) and restore, from the UI or the CLI; a safety snapshot is
  taken before a restore.
- Resource alerts: notifications (bell, ntfy, Telegram, webhook) when a disk passes 85 % (critical at 95 %) or, from the last week's trend, will be full within 14 days (the Overview disk tile shows "full in ~N days" when it is under 60), memory stays at 90 % or more for 5 minutes, CPU for 15 minutes, a disk runs low on inodes (85 %), the 15-minute load stays at twice the core count (the Overview shows a Load tile), or a container crashes, restarts in a loop or fails its health check, or publishes a port on every network interface (Docker bypasses ufw for those; the Health check lists them too). Fixed thresholds, one switch per kind in Settings → Notifications.
- App settings: apps with changeable options (time zone, sign-ups, mail servers, media folders...) have a **Settings** button on the Apps page. Saving validates the values, rewrites the app's `.env` and recreates its containers; if the app does not come back healthy the old values are put back. Passwords, ports and the public address are not editable there, and each change is written to the audit log (key names only, never values).
- Removing apps: **Stop & remove containers** keeps the data and the app stays in the list as stopped. On a stopped app that has no Public URL, **Delete app** removes it completely (containers' volumes and the data folder, after a confirmation; its backups are kept).
- Needs between apps: **Needs** on an app lets you tick the other apps it depends on (a database stack, say). Dockwren then names the apps affected in the confirmation before you stop or delete one, shows a need that is not running, and **Start** (on a stopped app) starts its needs first. It never changes how Docker runs the stacks.
- Resource limits: every app has a **Resources** button to cap the memory (e.g. `512m`, `2g`) and CPUs (e.g. `1.5`) of its main service (not helpers like the database). Limits are kept per app, survive updates, and apply on save by recreating the containers; if the app does not come back healthy the old limits are put back. Empty fields remove the limit. Changes are written to the audit log.
- Duplicate an app: on the Restore page, type a new name and press **Duplicate from selected snapshot**. The snapshot is restored into a second app with its own name and ports (data, accounts and passwords included; the original keeps running untouched). The copy gets no public hostname, and settings inside the app (a site URL, a domain) may still name the original address. Skipped for apps with fixed network ports or when memory is low. Take a backup first if the app has none.
- Image vulnerability scan: once a day every app's images (and the bundled Caddy image, while any app is published directly) are scanned with [Trivy](https://trivy.dev) (a pinned image run in a throwaway container with no access to the Docker socket; it reads the images from their registry and downloads Trivy's public vulnerability database, cached in `trivy-cache/` of the data directory). The Apps page shows the HIGH and CRITICAL counts per app ("2 critical, 5 high"; each CVE counted once). A notification is raised only for critical findings that already have a fixed version, and again when a new one appears; findings without a fix stay quiet. Nothing is changed: fixes arrive as image updates through Dockwren releases. Run one by hand with `dockwren scan <instance>`. Switch in Settings → Notifications.
- Public address check: every 5 minutes the panel requests each app's public hostname from outside the app (DNS and tunnel included). Three failed checks in a row raise a notification, and the Apps page shows reachable or unreachable next to the address, with the share of reachable checks over the last 30 days. An app is watched after its first successful check. Switch in Settings → Notifications.
- Log size cap: every container's Docker log is capped at 10 MB x 3 files (`compose.logging.yaml`, regenerated on install and update), so a chatty app cannot fill the disk. Apps installed with an older Dockwren show a **Cap logs** button on the Apps page; it recreates the containers and removes the cap again if the app does not come back healthy.
- Passwords: apps with a generated admin password get a **Passwords** button on the Apps page. After you enter your panel password (and 2FA code) again, it shows the password stored at install. Most apps apply that password only at first start, so if you changed it inside the app, the real one is the one you set there. Apps that read it on every start (Pi-hole) also get **Rotate and restart**: a new value, containers recreated, the old value put back if the app does not come back healthy.
- Update preview: **Update available** first shows what the update would do (image version changes, a link to the upstream release notes, new or unused images, migrations, whether a snapshot is taken, and a refusal such as a database major jump) with an **Update now** button. Nothing changes until you press it.
- Bulk actions: tick apps on the Apps page and use **Back up ticked** or **Update ticked**. They run one after the other, each as its normal job (snapshot first, rollback on a failed update); bulk update leaves skipped versions and unhealthy apps alone and skips the per-app preview. The result lists each app as done, failed or left alone.
- Config export/import (server move or disaster recovery): `dockwren export FILE` writes every app's configuration (compose files, `.env` with its passwords, limits, state; not the data) into one file encrypted with a passphrase (ChaCha20-Poly1305, key from Argon2id; at least 12 characters; given in `DOCKWREN_PASSPHRASE` or on the first line of stdin). The same file can be downloaded from Settings → Backups → Config export (passphrase typed there; asks for your panel password and 2FA code again). On the new server `dockwren import FILE` recreates the apps with their original passwords and starts them empty (apps that already exist are skipped); then `dockwren backup pull <app>` and `dockwren restore <app>` bring the data back. Public addresses are not recreated by `import`: it prints the `dockwren expose` line to run. `recover` publishes them again by itself once an app's data is restored (Cloudflare token from the export; the tunnel's connector must run on the new server), except for apps that started empty, which print the line instead. The export also carries the panel settings: the admin password hash and 2FA, notification channels, backup schedule, OS-update switch and the Cloudflare token. `dockwren import` writes those only when the file is absent on the new server; `dockwren recover` replaces them (and signs every old session out), so you sign in with your old password and 2FA after restarting the panel. Exports made by older versions lack them. Whoever can open the file can take over the panel, so keep it as safely as a password manager export. The off-host backup target (its credentials and repository password) is not in the file: connect it again in Settings, or copy `offsite.toml` into the data directory, before `backup pull`. The file must be readable by the panel user (put it in the data directory).
- Third-party templates: Settings → Updates → Third-party templates (or `dockwren template add <https-url> <full-commit-hash>`) adds an app template from a git repository (`manifest.toml` + `compose.yaml`, optional `icon.svg`, at the top level; needs `git` on the server). Only a full commit hash is accepted, so nothing changes under you; Dockwren fetches that commit (no hooks, no submodules, no checkout), runs the usual template checks plus stricter Compose rules (no devices, extra privileges, long-form mounts or inline port/volume lists), refuses templates that run commands inside containers (`post_start`, `migrations`) or reuse a built-in id, and shows you the files before you click Add. These apps are labelled third-party in the catalog. The checks are simple text checks, not a sandbox: read the files and trust the images. Adding or removing one in Settings takes effect at once; after `dockwren template add` or `remove` on the command line, restart the panel.
- Health check: Settings → System → Health (or `dockwren doctor` in a terminal, exit code 1 on a failure) runs read-only checks of what Dockwren depends on: Docker and Compose versions, a private and writable data folder, free disk and memory, clock sync, DNS and a connection to Docker Hub, off-host backup age and whether Cloudflare is connected. It changes nothing.
- Scheduled stop/start per app: **Schedule** on an app sets a daily stop time and/or start time (UTC). A stop works like Remove (containers go, data stays) and waits until no running app needs it; a start only happens for an app the schedule stopped, with the apps it needs first. A manual start or stop in between is not undone.
- Drift detection: an app whose running containers no longer match its Compose files (edited by hand, a container removed or replaced) shows "out of sync" with the services that differ; **Apply** recreates only those (`docker compose up -d`).
- Stack version history: every successful **Edit stack** keeps the Compose file and environment it replaced (the newest 20). Load an earlier version into the editor, see what differs, and apply it through the usual checks, backup and rollback.
- Private images: Settings → System → Registry logins saves a login for GHCR, Docker Hub or your own registry (user plus an access token, checked with the registry, kept in a private file on the server, not part of the config export). Installs, updates and adopted stacks then pull private images with it; **Log out** removes it.
- Scheduled backups: Settings → Backups → Scheduled backups takes a snapshot of every app daily or weekly (UTC hour of your choice) and keeps the newest N per app (default 7). **Back up now** on the Apps page takes one on demand and the table shows each app's last backup. Apps that are stopped or not healthy are skipped. A failed run raises a notification. Tick **Update apps automatically** to move healthy apps to a newer bundled template, only inside the UTC window you set (default 03 to 06; equal hours mean any time; each update snapshots first and rolls back on failure; a failed version is not retried until Dockwren restarts; a success raises an "updated automatically" notification and a failure a failed-update one; off by default). On any pending update, **Skip this version** removes its notification and keeps auto-update away from it until a newer release appears; **Stop skipping this version** undoes it. Each scheduled snapshot is then checked automatically: dumps must be present and non-empty, and `files.tar.gz` is read end to end (gzip checksum, tar structure, every backed-up path present); a failure raises a notification. You can check any snapshot by hand with **Verify selected snapshot** on the Restore page or `dockwren verify <instance> [snapshot]`; it changes nothing and the app keeps running (it does not start a copy of the app, so it proves the snapshot is intact, not that the app boots from it). For that, tick **Test restores** in the same form: about once a week, after the scheduled backups, each healthy app's newest snapshot is restored into a throwaway copy (own name and ports, in `restore-test/` of the data directory), must come up healthy, and the copy is deleted again; a failure raises a notification. Skipped when less than 1 GiB of memory is free or the app uses fixed LAN ports. Run one by hand with **Test restore** on the Restore page or `dockwren restore-test <instance>`; the running app is never touched. These snapshots live in the data directory, so on their own they only protect against mistakes, not disk loss; add an off-host target (next item).
- Disk usage: Settings → System → Disk usage lists each app's data folder, old restore copies, local snapshots and images (an upper bound; a "+" marks files owned by another user that could not be counted), with explicit buttons to free space: keep only the newest 3 local snapshots of an app (off-host copies are untouched), remove Docker images no container uses, and delete unused Docker volumes and networks (listed with sizes first; anything an installed app declares or labels, even while the app is stopped, is never offered, and if an app's compose file cannot be read nothing is offered at all).
- Off-host backups: Settings → Backups → Off-host backups uploads a copy after every backup to another server (SFTP) or an S3-compatible bucket (AWS, Backblaze B2, Wasabi, MinIO...), encrypted and deduplicated with [restic](https://restic.net) run in a throwaway container (nothing to install). The settings are tested before they are saved. Dockwren generates the repository password and shows it **once**: store it in your password manager, without it the copies cannot be read. Credentials stay in a private file in the data directory and are never shown again. Disk lost? The Restore page has a **Fetch snapshots from off-host** button, and on a new server you connect the same target with the same password, then `dockwren backup pull <app>` brings the snapshots back. Recreate the app with `dockwren import` (a snapshot holds its data, not its settings or passwords; see config export/import below) and run `dockwren restore <app>`; it replaces the fresh data with the backed-up data, so the app comes back with its original accounts and content. After every backup a config export (compose files, `.env` passwords, settings; no data) is uploaded to the same target, sealed with the repository password. **Whole server lost?** On the new server run `dockwren recover`: it asks for the off-host target (SFTP or S3 details and the repository password; or set `DOCKWREN_OFFSITE_KIND`, `_ENDPOINT`, `_BUCKET`, `_ACCESS_KEY`, `_SECRET_KEY`, `_HOST`, `_PORT`, `_USER`, `_PATH`, `_PRIVATE_KEY_FILE`, `_PASSWORD`), downloads the export, recreates every app and restores its newest snapshot. Apps that fail are listed and the rest still finish. A failed upload raises a notification; the local snapshot is kept.
- Cloudflare Tunnel publishing with DNS conflict handling and optional Cloudflare Access (see [Publishing](PUBLISHING.md)).
- Direct HTTPS without Cloudflare: a bundled Caddy container gets a Let's Encrypt certificate and serves the app on ports 80/443 (see [Publishing](PUBLISHING.md)).
- Port audit: besides containers that publish a port on every interface, the Health section and a notification flag any other host socket listening on every interface (for example a host-network container or a stray service). ssh (22) and, while the Caddy container runs, 80/443 are expected; add more with `DOCKWREN_LISTEN_ALLOW` (comma-separated ports). The message names the likely owner: the process when it is one of the panel's own, otherwise the running host-network containers (root services stay unnamed, since the panel does not run as root).
- `dockwren set-password` to rotate the admin password.
- Web terminal (optional, off by default): a shell inside the containers of apps Dockwren installed, from the Containers page. Turn it on in Settings (or force it with `DOCKWREN_TERMINAL=1`); it asks for your password (and 2FA code) each time, is logged and shown in Notifications. Not a host shell.
- Audit log: Settings → Security lists the newest events (sign-ins, failed and locked-out attempts with the source address, app install/update/backup/restore/remove/publish, 2FA and terminal changes, Cloudflare and notification settings, OS and panel updates). It is stored as `audit.log` in the data directory (about the last 2000 lines) and never contains passwords, tokens or codes.
- Panel self-update: Settings → General shows when a newer release exists. Run `sudo dockwren self-update` once (it updates right away and enables the button; installs made with the current `install.sh` already have it). After that the **Update Dockwren now** button asks for your password (and 2FA code), restarts the panel, and a root-run systemd hook downloads the release from GitHub itself, checks the binary against the published `SHA256SUMS`, and swaps it in, keeping the old one as `dockwren.prev` (roll back with `sudo mv /usr/local/bin/dockwren.prev /usr/local/bin/dockwren && sudo systemctl restart dockwren`). The panel never hands a binary to root. Apps keep running.
- Sign-in alerts: a notification when someone signs in from an address that has not signed in before (the first start after upgrading learns the addresses already in the audit log, so it stays quiet), and when five wrong passwords or codes lock sign-in for a minute. Two switches in Settings → Notifications; the Audit log has the details.
- UPS (optional): plug a USB UPS into the server and Settings → System → UPS shows it (grey "Not detected", amber "Detected, not set up" with the one command to run, green "Connected" with charge, runtime and load, then "On battery" or "Battery low"). `sudo dockwren setup-ups` installs NUT (Network UPS Tools, apt), finds the UPS, writes a standalone configuration, fixes the USB permissions and enables a clean shutdown when the battery runs low; it never touches an existing NUT setup and can be run again. Once NUT answers, Dockwren reads it every 10 seconds over NUT's local read-only port and notifies you (bell, ntfy, Telegram, webhook) when the power is cut and the UPS runs on battery, when the battery is low and the server is about to be shut down by NUT, when the battery needs replacing, or when the UPS is overloaded; it clears when the condition ends. Health shows the UPS (charge, estimated runtime, load). NUT itself shuts the server down; Dockwren never does. Without a UPS or NUT the panel stays quiet. See `DOCKWREN_NUT` in [OPERATIONS.md](OPERATIONS.md).
- Disk health (optional): the panel cannot open disk devices, so `sudo apt install smartmontools` and `sudo dockwren setup-smart --data-dir <your data dir>` once installs a root systemd timer that runs `smartctl` every hour and writes a short summary (`smart.json`, no serial numbers) into the data folder. Health then shows each disk (verdict, temperature, wear, power-on days) and a notification fires on a failed health test, pending or uncorrectable sectors, NVMe critical warnings, low spare capacity, 90% wear or over 65 °C. Not set up, nothing shows (virtual servers have no SMART). See [SECURITY.md](../SECURITY.md).
- OS updates (optional, off by default): the panel always tells you when the server has pending package updates or needs a reboot. To install them from Settings too, run `sudo dockwren setup-osupdate --data-dir <your data dir>` once, then turn it on in Settings. Each start asks for your password (and 2FA code); it runs `apt-get update` and `apt-get full-upgrade` as root through a small systemd helper, shows the log live, and never reboots. Debian and Ubuntu only. See [SECURITY.md](../SECURITY.md).
- Installable: in Chrome, Edge or Safari use "Install app" / "Add to Home Screen" and Dockwren opens in its own window with its icon. It needs a live connection (no offline mode), and browsers only offer this over HTTPS or on localhost.
- Two-factor sign-in (optional): turn it on in Settings with any authenticator app (Google Authenticator works). You can also add **passkeys** (fingerprint, security key or phone) under Settings → Security: after the password, sign-in asks for the passkey instead of a code. A passkey is bound to the hostname it was added from (not an IP address) and works only there; the authenticator code and recovery codes work on any address (recovery codes are made when you add your first passkey without an authenticator app). Locked out? `dockwren disable-2fa` turns off the authenticator app, recovery codes and passkeys.
